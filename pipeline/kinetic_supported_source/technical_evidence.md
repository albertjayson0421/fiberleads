# Technical evidence — public search endpoint is browser-behavioral-bound

**Endpoint:** `POST https://buy.gokinetic.com/api/v1/address/search`
**Date:** 2026-09-09 (UTC)  ·  **Route tested:** US residential (Spectrum 35.150.152.134) and US-residential proxy exits (T-Mobile, Verizon Business — non-datacenter, verified).

## Proven, not inferred
Same residential browser, same valid bearer token, same cookies, same exact request body:

| request construction | result |
|---|---|
| native app request (browser, with behavioral proof headers) | **HTTP 200** |
| valid token + `device-id` + `session-id` + exact body, **no behavioral headers** | **HTTP 403 "Forbidden"** |
| add `x-meta-info` + `x-resource-id` + `x-interaction-quality` + `x-quality-flag` | **HTTP 200** |

So the 403 is caused specifically by the missing behavioral-proof headers — not the token,
not device/session ids, not the request body schema.

## Where the headers come from
`_app-<hash>.js` builds the request headers: `device-id`/`session-id` from `localStorage`
`session-store`; and `x-meta-info` / `x-resource-id` / `x-interaction-quality`
(`interactionQuality.toFixed(3)`) / `x-quality-flag` (`qualityFlag`) from a behavioral
detection store. The page loads a PerimeterX/HUMAN sensor (`spx?dxver=4.0.0&shaid=36232`) and
Google reCAPTCHA. These headers are proof-of-humanity artifacts generated by a real browser
observing real interaction.

## Not our implementation
A single stable server-side client (one session, US residential egress, correct
Origin/Referer/Fetch-Metadata, no churn) authenticates fine (HTTP 201) but is refused at search
(HTTP 403). Our original run completed 209,526 addresses before this behavioral layer was added;
it was added after, which is why prior automation succeeded and now returns 403.
